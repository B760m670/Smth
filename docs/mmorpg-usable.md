# Что из этой песочницы годится для MMORPG

Продолжение [разбора исходников](threejs-vfx-sandbox-analysis.md). Тот документ
отвечал на вопрос «как это устроено». Этот — на вопрос «что из этого выживет,
когда на экране будет не один кастер, а сорок, и половина из них — по сети».

Короткий вердикт: **ядро архитектуры годится, причём годится необычно хорошо;
почти вся периферия — нет.** Ниже — что брать, что переписывать, что не трогать,
и с какими цифрами.

## 1. Стратегический аргумент для инди-команды

Это не эстетская поза, а экономика, и её стоит проговорить до того, как решать,
что копировать.

**Художника по текстурам для боевых эффектов не нужно вообще.** Ни одного
спрайт-листа, ни одного флипбука, ни одной noise-текстуры. Для инди-команды, где
VFX-артиста обычно нет в принципе, это разница между «есть боёвка» и «нет
боёвки».

**Размер загрузки.** Бандл — 1.1 MB (298 kB gzip). Все шесть заклинаний со всеми
их частицами, декалями, ожогами и материалами весят ноль байт трафика сверх кода.
Для MMO, где клиент качают перед первым входом, это ощутимо: типичный
спелл-эффект на флипбуках — это 2–8 MB атласов на заклинание.

**Реколоры бесплатны.** Каждое заклинание экспонирует *каждый* цвет, которым
рисует, и ни один не выводится из другого. Ранги заклинания, сезонные скины,
фракционные варианты, «легендарная» версия — это JSON на 40 строк, а не новый
атлас. Для MMO с прогрессией и монетизацией косметики это прямо в цель.

**Тюнинг на паузе.** Геймдизайнер жмёт `P` посреди взрыва и правит силуэт по
неподвижному кадру. Это цикл итерации, который обычно требует внешнего
VFX-редактора и билда.

**Цена:** всё это платится GPU-временем на фрагмент. Процедурный шум дороже
сэмпла текстуры. При одном кастере это не видно; при сорока — станет главным
бюджетом. См. раздел 4.

## 2. Свойство, ради которого стоит смотреть на этот код: каст сериализуется в ~20 байт

Это самое ценное, что здесь есть для сетевой игры, и получилось оно случайно —
как побочный эффект правила «никаких размерностей на CPU».

`ThunderAbility` за весь каст захватывает **одно число**:

```js
onSpawn() {
  ...
  // The one thing a cast captures. Everything else is resolved per frame.
  this._seed = Math.random() * 100;
}
```

`BeamAbility`, `SnareAbility`, `GlacierAbility` — то же самое. `IceAbility` и
`MeteorAbility` держат пул безразмерных бросков, которые тоже выводятся из сида.
Всё остальное — путь молнии, веер нитей, изломы, ширина, фазы, цвета — чистая
функция от `(origin, direction, distance, seed, t)` и профиля заклинания.

Для MMO это означает вот что:

```
CastPacket {
  casterId  u32
  spellId   u16
  rank      u8
  originXZ  2 × f32   // или квантованные i16
  dirYaw    u16       // квантованный угол
  distance  u16       // квантованные метры
  seed      u32
  t0        u32       // серверный тик начала
}
≈ 24 байта
```

Реплицируется **намерение**, а не эффект. Никакой синхронизации частиц, никаких
снапшотов состояния VFX, никакого дрейфа. Клиент, получивший пакет, разворачивает
из него точно тот же болт, который видит кастер, — и, что важнее, клиент,
**вошедший в зону видимости посреди каста**, стартует эффект с правильной фазы,
просто подставив `t = now - t0`.

Это, кстати, единственная причина, по которой параметрические меши (раздел 5.1)
для MMO не просто «красиво», а функционально: у эффекта, чья форма — функция
времени, а не результат интегрирования, есть корректный «вход в середину».
Система частиц с CPU-интегрированием такого не умеет — там нужно либо
перематывать симуляцию, либо мириться с тем, что опоздавший зритель видит эффект
с нуля.

**Что для этого надо доделать:**

* `Math.random()` в `onSpawn` заменить на seeded PRNG (mulberry32 / xorshift от
  `seed`), иначе броски костей на разных клиентах разойдутся. Косметически это
  почти не заметно, но воспроизводимость багов и запись реплеев ломается сразу.
* `frame.uTime` — сейчас это локальный аккумулятор, умноженный на
  `settings.global.timeScale` и замораживаемый паузой. Нужен **серверный клок**:
  `uTime` = синхронизированное время, а `timeScale`/пауза остаются только в
  оффлайн-режиме редактора. Иначе чужие касты будут играть не в той фазе.

## 3. Одно архитектурное изменение, без которого ничего не поедет

`settings` — глобальный синглтон, и каждая абилка читает `settings[this.element]`:

```js
get config() {
  return settings[this.element];   // ← все инстансы ice читают ОДИН объект
}
```

В песочнице кастер один, и это идеально. В MMO это ломается на первом же
сценарии: два игрока кастуют Frost Lance разных рангов, или один в «ледяном»
скине, а второй в «кровавом», или на одном висит бафф, растягивающий эффект.
Читать глобальный объект нельзя — нужен **профиль на каст**.

Хорошая новость: правило «читать каждый кадр, ничего не захватывать» при этом
сохраняется полностью, меняется только *откуда* читать. Изменение маленькое и
локальное:

```js
// было
get config() { return settings[this.element]; }

// стало
spawn(origin, direction, distance, profile) {
  this.profile = profile;           // ссылка на общий неизменяемый объект
  ...
}
get config() { return this.profile; }
```

`profile` — это тот же по форме объект, что сейчас лежит в `settings.ice`, но их
теперь много: по одному на (заклинание × ранг × скин). Они живут в реестре,
грузятся из JSON и **шарятся по ссылке** — тысяча одновременных кастов Frost
Lance ссылается на один объект, никакого копирования.

Что при этом остаётся работать:

* **Редактор.** Он мутирует объект профиля на месте — ровно как сейчас мутирует
  `settings.ice`. Все касты, ссылающиеся на этот профиль, обновляются в тот же
  кадр. Тюнинг на паузе выживает.
* **Пресеты → спеллбук.** `PresetManager` уже сериализует дерево настроек в
  читаемый JSON и грузит его обратно deep-merge'ем **внутрь** живых объектов
  (`applySettings`), сохраняя идентичность. Это буквально готовый
  data-driven-пайплайн для описания заклинаний, просто он сейчас применяется к
  одному глобальному дереву вместо реестра профилей.
* **Материалы.** Здесь есть подвох: `material.userData.sync()` читает
  `settings.ice` напрямую и материал у трёх мешей кристаллов **общий**. Значит
  `sync` должен принимать профиль аргументом (как уже делает `LightningMaterial`,
  которому состояние передают объектом `state` — это правильный образец), а
  материалы, чьи uniform-ы различаются между кастерами, надо либо клонировать
  на профиль, либо переводить на инстансированные атрибуты. Для `IceMaterial` и
  `GlacierMaterial` второе честнее: палитра уезжает в per-instance атрибуты, и
  два игрока с разными скинами рисуются одним draw call'ом.

Это, на мой взгляд, самая важная правка во всём списке. Дальше — вопросы
производительности, а это вопрос корректности.

## 4. Где оно точно сломается, с цифрами

### 4.1 Декали — стена номер один

`DecalSystem` **не имеет никакого лимита**. `spawn()` всегда берёт из пула,
`ObjectPool.acquire()` при пустом пуле просто создаёт новый объект. Каждая декаль
— отдельный `Mesh` со **своим** `ShaderMaterial` (программа общая, uniform-ы
свои), `frustumCulled = false`, то есть **один draw call на декаль, всегда**.

Считаем один каст Frost Lance на полную дальность:

```
frostRate = 3.6 патча на метр × range 15 м = 54 декали
frostLife = 7 секунд
```

Плюс ударная волна и широкое пятно инея — **56 draw calls, живущих 7 секунд, с
одного нажатия клавиши**. Storm Lance: `arcRate 0.9/м × 24 м` = 21 ожог + 21
пятно копоти + 4 на удар = 46, копоть живёт 6.5 с.

Десять игроков, спамящих Frost Lance в замесе, — **больше 500 draw calls только
на декали**. Это выше, чем весь остальной кадр.

**Что делать:**

1. Инстансинг. Тип декали — это `#define DECAL`, значит один инстансированный меш
   **на тип**: `uAge`, `uSeed`, `uRadius`, `uColorA/B` уезжают в per-instance
   атрибуты. 500 декалей одного типа → 1 draw call.
2. Жёсткий кап с вытеснением по LRU (скажем, 128 на тип), и приоритет: свои
   декали и декали по цели живут дольше чужих.
3. Реальные bounds вместо `frustumCulled = false` — декаль знает свой радиус и
   позицию, посчитать сферу тривиально.
4. Дистанционный LOD: дальше N метров декали не спавнятся вообще. Их всё равно
   не видно, а платит за них весь кадр.

### 4.2 Динамический свет — стена номер два

`LightPool` — шесть `PointLight` на всю сцену, и это не жадность, а
принципиальное ограничение forward-рендера three: **число источников входит в
ключ кэша программы**, поэтому добавление света перекомпилирует все материалы.
Авторы решили это правильно (создать 6 на старте и парковать на нулевой
интенсивности), но 6 — это бюджет на одного кастера. Nova Beam берёт **два**
(колонна и руки). Три игрока с лучами — пул исчерпан, `acquire()` возвращает
`null`, и все обращения к хэндлу защищены — то есть эффект просто останется без
света, молча.

**Что делать:** приоритетная выдача (свой каст → каст пати → чужой, дальше —
по дистанции и интенсивности), с перехватом света у менее важного эффекта.
Дальним кастам свет не нужен вовсе — им хватит эмиссивной геометрии, которая у
всех этих эффектов и так есть. Радикальное решение — WebGPU-бэкенд three с
кластерным освещением, но это отдельный крупный разговор.

### 4.3 `frustumCulled = false` — 22 места

Все параметрические меши (болт, труба, катушки, диски, клетка, кольцо дальности,
декали, всплески) отключают отсечение и ставят `boundingSphere` радиусом 1e4.
Иначе никак: геометрия живёт в parameter space, её собственные границы ничего не
значат.

При одном кастере это бесплатно. При тридцати — вершинные шейдеры всех эффектов
за спиной у камеры крутятся каждый кадр, а у болта это 72 сэмпла × 24 нити ×
5 октав шума.

**Что делать:** считать честную сферу на CPU из того, что и так известно —
`origin`, `target`, максимальный `spread`/`radius`. Одна строка на каст, полное
отсечение вместо никакого.

### 4.4 Объёмный огонь — не тиражируется

`VolumetricFireMaterial` — 72 шага рейтмарша **на фрагмент**, на камера-ориентиро­
ванном хулле, который занимает изрядную часть экрана, когда метеор летит на тебя.
Один метеор — прекрасно. Пять одновременных — филлрейт кончится.

**Что делать:** это кандидат номер один на LOD-лестницу. Ближний свой каст —
полный рейтмарш; чужой в 20 метрах — тот же proxy-hull с дешёвым «плоским»
шейдером в 12 шагов; дальше 40 метров — облако частиц с тем же градиентом.
Переключение по дистанции и по «мой/чужой».

Общее правило, которое стоит принять сразу: **рейтмарш — привилегия, а не
техника по умолчанию.** В MMO он допустим для боссовых способностей и своих
ультимейтов, но не для того, что кастуют каждые 8 секунд сорок человек.

### 4.5 Плоский пол зашит в шесть мест

Допущение «земля — одна плоскость на `y = 0`» сидит в:

* raycast прицела (`GROUND_PLANE = new Plane(new Vector3(0,1,0), 0)`);
* `Ability#spawn` — `this.origin.set(origin.x, 0, origin.z)`;
* декали (квад на `y = height`, где height ≈ 0.02);
* круг far cast (квад на `y = 0`);
* поле ловушки и лист льда Glacial Crown;
* щупальца и дуги обода, которые клампятся к `uTendrilHug`.

Авторы это честно перечисляют в «известных шероховатостях». Для MMO с рельефом
нужно:

* raycast по коллайдеру ландшафта вместо математической плоскости;
* декали — либо проекция (дороже), либо конформный меш: сетка 8×8 вместо квада,
  высота вершин сэмплится из хайтмапа в вершинном шейдере. Второе дешевле и
  вписывается в местную философию;
* поле/круг — то же самое;
* наземные роли клетки — сэмпл высоты в `pathAt()` вместо константы.

Заклинания, которые целиком в воздухе (Storm Lance, Nova Beam), переезжают
без изменений.

### 4.6 Мелочи, которые всплывут

* `ParticleEngine.countLive()` обходит **65 200 слотов** линейно. Сейчас зовётся
  только на интервале статистики HUD — так и оставить, но не соблазняться звать
  каждый кадр.
* Общая ёмкость частиц — 65 200 слотов × 17 float = **~4.4 MB** атрибутных
  буферов. Это фиксировано и **не растёт с числом игроков** (системы общие по
  имени) — редкий случай, когда решение из песочницы масштабируется лучше, чем
  ожидаешь. Ёмкости под MMO надо поднимать, но линейно и осознанно.
* `MAX_CONCURRENT = 4` — общий на все типы, снимает самый старый каст. В MMO это
  должен быть бюджет-менеджер с приоритетами, а не FIFO на четыре слота.
* Тряска камеры и полноэкранная вспышка сейчас срабатывают от **любого** каста.
  В MMO их надо фильтровать: свой каст, попадание по мне, взрыв в радиусе N.
  Иначе в замесе экран превратится в стробоскоп — это не гипотетика, это
  типичная болезнь MMO-боёвок.
* Прозрачность и аддитив: 23 системы частиц, декали, ленты, трубы — всё
  transparent. При двадцати кастерах овердро становится главным расходом.
  Стандартное лекарство — рисовать VFX в half-res буфер и апскейлить; depth
  prepass для этого уже есть.

## 5. Что брать почти как есть

Отсортировано по отношению «польза / риск».

### 5.1 Parameter-space геометрия — забрать целиком

Лента `(t, side)`, труба `(t, a)`, инстансированный аннулус `(band, a)`,
многоролевая клетка. Это ядро ценности проекта. Причины для MMO уже перечислены:
форма — чистая функция времени, значит корректный вход в середину каста, значит
дешёвая репликация. Плюс: два draw call'а на болт любой сложности, `strands`
почти бесплатны, и число нитей можно **снижать по дистанции как LOD** без
единого изменения в логике — это просто `geometry.instanceCount`.

### 5.2 Система частиц — забрать целиком

* системы общие по имени, а не по владельцу → VRAM не растёт с числом игроков;
* кольцевой буфер → спам абилок перерабатывает слоты, а не аллоцирует;
* аналитическое затухание (`(1 - exp(-k·age))/k`) → точное, не зависит от FPS,
  и, что важно для сети, **позиция частицы — функция возраста**, а не результат
  интегрирования. Опоздавший зритель снова получает правильную картинку;
* мёртвые частицы выбрасываются за клип-объём — треугольник отбрасывается до
  растеризации;
* шесть процедурных силуэтов через `#define`;
* `RateEmitter` с дробным накоплением и капом 240/кадр.

Единственное, что надо добавить, — глобальный бюджет: множитель `particleCount`
по дистанции и по настройке качества. Хук для этого уже есть
(`settings.global.particleCount`), надо только сделать его per-cast, а не
глобальным.

### 5.3 Инфраструктурные мелочи, которые вы всё равно напишете сами — и хуже

* **`FrameUniforms`** — раздача одних и тех же `{ value }` боксов по идентичности.
  Одна запись за кадр обновляет десятки материалов.
* **`utils/color.js`** — мемоизация `#rrggbb` → `THREE.Color`. Без неё
  редактор цветов churn'ит GC на каждом кадре.
* **`RibbonGeometry`** с опцией `frame` (пишет `aCenter`/`aTangent`) — готовый
  proxy-hull для любого объёмного эффекта вдоль кривой.
* **`shaders/lib/noise.glsl.js` и `common.glsl.js`** — симплекс, fbm, ridged,
  curl, вороной, `softFade`, `dissolveMask`, `gradient4`, `aastep`. Это ваша
  шейдерная стандартная библиотека, можно брать дословно.
* **`utils/shaderPatch.js`** — композиция `onBeforeCompile` вместо молчаливого
  затирания. Обязательно, как только патчей станет больше одного.
* **`utils/dispose.js`** и дисциплина «каждая система имеет `dispose()`». В MMO,
  где зоны стримятся, а не грузятся один раз, это не роскошь.
* **`CameraShake`** — trauma², квадратичный спад, сумма синусов на
  несоизмеримых частотах. Хорошо ощущается, 68 строк.
* **`ScreenFlash`** — состояние без единого draw call, читается пассом грейда.
* **Depth prepass + `softFade()`** — обязателен. Без него любой эффект режет
  землю и персонажей прямой линией, и это первое, что замечают в бете.

### 5.4 Пайплайн персонажа — три конкретных грабли уже обойдены

`CharacterController` и `AssetLoader` решают то, на что обычно уходит день:

* **нормализация роста рига**: `FBX_SCALE = 0.01` (Mixamo в сантиметрах), затем
  пересчёт масштаба под `TARGET_HEIGHT = 1.78` по реальному bounding box, затем
  посадка на `y = 0` и центрирование по XZ. Для MMO с несколькими расами и
  ригами из разных источников это ровно тот код, который нужен;
* **измерение yaw бинд-позы** (`_forwardYaw`): бинд-позы не обязаны смотреть в
  `+Z`, и `setFacing` вычитает собственный разворот рига, чтобы для вызывающего
  «0 = смотрит в +Z» было правдой независимо от того, как экспортировали FBX;
* **клипы из чужих файлов**: миксер биндит треки **по имени кости**, поэтому
  анимация, авторенная в другом экспорте того же скелета, играет без
  ретаргетинга. Дубликат рига выбрасывается сразу после извлечения клипа;
* **`AssetLoader`** перехватывает абсолютные пути, запечённые авторинг-тулами в
  FBX (`C:/Users/.../textures/...`), и подсовывает белый 1×1 PNG вместо вечно
  висящего запроса. Это боль, с которой сталкивается каждый, кто грузит FBX из
  Blender/Maya/Mixamo.

Чего здесь **нет** и что придётся писать: стейт-машина анимаций, локомоция,
root motion, слои/маски (верх тела кастует, ноги бегут), сетевая интерполяция
чужих персонажей, IK. Сейчас персонаж стоит на месте и дышит.

### 5.5 Дизайн-уроки, которые дороже кода

В комментариях зафиксирован ряд решений, каждое из которых куплено попыткой
сделать иначе. Для MMO, где на экране одновременно сорок эффектов и читаемость —
вопрос выживания боёвки, они дороже любого шейдера:

* **Круг обещает footprint и держит обещание.** Толстая граница индикатора
  разбита относительно номинального радиуса через `boundaryBias`, а не
  отцентрована на нём: игрок судит о том, *где кончается эффект*. Тот же радиус
  потом используют щупальца, дуги, поле и лист льда — одно число, `zoneRadius`,
  читается в одном месте на потребителя и нигде не копируется.
* **Snap-out вместо линейного роста.** «Круг, растущий линейно, читается как
  элемент UI; перелетающий свой радиус и оседающий обратно — как действие
  кастера».
* **Середина остаётся пустой.** У Glacial Crown ничего не сажается в центре
  круга, потому что читается стена, в которую смотришь: заполните диск — и
  кольцо перестанет быть кольцом.
* **Два морозных заклинания различаются материалом, а не палитрой.**
  `GlacierMaterial` написан от противного к `IceMaterial` намеренно: «две
  морозные абилки на одной панели должны различаться раньше, чем это сделает
  силуэт, а перекраски недостаточно». В MMO с деревом талантов, где у одной школы
  бывает по восемь заклинаний, это правило спасает всю школу от каши.
* **«Луч, который изламывается, — это молния».** Storm Lance и Nova Beam делят
  цветовую семью, а различает их только характер движения: piecewise-linear шум
  с сохранёнными углами против гладкого, вытянутого вдоль потока и ползущего
  вниз по стволу.
* **Никогда не сэмплировать шум по `atan(y, x)`.** Урок повторён в коде дважды
  (наземные ожоги болта, поле ловушки): угловой лукап даёт всем радиусам вдоль
  пеленга одно значение и рисует прямые спицы из центра — салют, а не ожог.
  Domain warp в плоскости.
* **Мягкий потолок Рейнхарда на сумме эмиссивных членов** (`glow /= 1 + glow*k`).
  Независимые члены, пикующие на одном скользящем угле, складываются в белое
  пятно. В MMO, где поверх всего ещё и блум, это случится тем более.
* **Не добавлять и не удалять источники света в рантайме.** Классическая причина
  фриза при спавне VFX в three.

## 6. Чего в проекте нет вообще

Это надо проговорить, чтобы не строить планов на пустом месте. Проект — **стенд
для авторинга визуала**, а не прототип боёвки. В нём отсутствуют:

* попадания, хитбоксы, цели, урон, статусы, аггро;
* сеть в любом виде — ни клиента, ни сервера, ни протокола;
* серверная авторитетность: кулдауны живут в `Map` на клиенте, дальность и
  минимальная дистанция проверяются локально в `AimController`, LOS не
  проверяется вообще;
* интерполяция и экстраполяция чужих персонажей;
* инвентарь, спеллбук как игровая сущность, прогрессия;
* UI за пределами HUD с шестью слотами и счётчиками;
* звук — ни единой строки;
* рельеф, коллизии, навигация, стриминг зон.

Реалистичная оценка: это примерно **визуальный слой боёвки, и только он** —
причём его самая трудная и самая редко хорошо сделанная часть. Всё остальное надо
писать с нуля, и это остальное — большая часть работы над MMORPG.

---

## 7. Порядок действий, если решаете брать

Первые три шага дают работающую основу; дальше — по мере надобности.

1. **Профили вместо синглтона** (раздел 3). Без этого второй игрок не появится.
   Заодно перевести `material.userData.sync()` на приём состояния аргументом —
   образец уже есть в `LightningMaterial`.
2. **Seeded PRNG + серверный клок** (раздел 2). После этого каст реплицируется
   24 байтами и корректно подхватывается в середине.
3. **Инстансированные декали с капом** (раздел 4.1). Самая большая единичная
   победа по производительности.
4. **Реальные bounds вместо `frustumCulled = false`** (раздел 4.3). Дёшево,
   быстро, заметно.
5. **Бюджет-менеджер VFX**: приоритет (свой / пати / чужой) × дистанция →
   уровень качества (полный / урезанные частицы / импостор / ничего).
   Прицепить к нему `particleCount`, число нитей, свет и декали.
6. **Рельеф** (раздел 4.5) — когда появится ландшафт.
7. **Half-res VFX-буфер** — когда упрётесь в филлрейт, но не раньше: депф-препасс
   уже есть, добавить буфер несложно, а раньше времени усложнять не стоит.

Отдельным треком — **превратить редактор в инструмент геймдизайнера**: реестр
профилей вместо одного дерева, экспорт в спеллбук, версионирование. Механика для
этого уже написана (`PresetManager` + `applySettings` с сохранением
идентичности), не хватает только слоя «много профилей».

## 8. Что не брать

* **`VolumetricFireMaterial` как общую технику.** Забрать под боссовые
  способности и ультимейты, обернув в LOD-лестницу. Не делать на нём рядовые
  заклинания.
* **Архив** (`src/archive/`, 7 115 строк: рейтмарченные пламя и вода, ветер,
  земля со сплайна). Как справочник по техникам — отлично, там есть вещи, каких
  нет в живом коде. Как код — он написан под старую спайн-базу `Ability`, которой
  больше нет, и портировать его дороже, чем переписать нужный кусок.
* **`transparent: true` + `depthWrite: true` на кристаллах.** В песочнице это
  осознанный компромисс (лёд почти непрозрачный, записи глубины не дают полю
  сортироваться сквозь себя), но авторы сами отмечают артефакты на низкой
  прозрачности. В замесе, где ледяных полей несколько и они пересекаются, это
  вылезет. Либо непрозрачный проход с alpha-test, либо отдельный отсортированный
  список.
* **`MAX_CONCURRENT = 4` и FIFO-вытеснение.** Заменить бюджетом с приоритетами.
* **Distortion-проход** в его нынешнем виде — он работает вхолостую, в него никто
  не пишет. Либо использовать (жар от огня, рефракция льда), либо выключить.

## Итог

Из этой песочницы стоит взять **дисциплину, а не файлы**: «никаких размерностей
на CPU», геометрию в parameter space, эффект как чистую функцию `(seed, t,
профиль)`, процедурный синтез вместо ассетов и общие системы частиц. Это ровно те
свойства, которые в сетевой игре превращаются в дешёвую репликацию, корректный
вход в середину каста, бесплатные реколоры под прогрессию и VRAM, не растущий с
числом игроков.

Периферия — декали, пул света, отсечение, бюджеты, допущение плоского пола —
написана под одного кастера на плоскости и в MMO требует переработки, местами
полной. Но это понятная инженерная работа с известными решениями, а не
исследование.

И главное, что стоит забрать бесплатно, — комментарии. В этом коде задокументированы
не решения, а **отвергнутые альтернативы**: почему не CSM, почему не `atan()`,
почему линейный шум, а не smoothstep, почему тупое температурное поле, а не
турбулентное. Каждая такая заметка — это чей-то вечер, которого у вас теперь не
будет.
